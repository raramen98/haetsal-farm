> 고객사: 15. 농산물 직거래 농가 "햇살농원" · 작성: 해라 · 2026-11-13

## 0. 한눈에 보기

```
[입력]  S-06 엑셀 업로드 · S-05 카톡/전화 입력(AI 정리) · S-12 어머니 전화 입력
   │
   ▼  (서버) R-1 번호 정규화 → 고객 묶기 / R-2 번호 없음 → '번호 확인 필요' / R-3 중복 의심
   ▼  (서버) R-6 남은 수량 검사 → 넘으면 거부 / R-7 판매 시작 전 → '예약'
   ▼  (서버) R-8 발송 예정일 계산 (15시 마감 · 월~목 · 판매 시작일)
   ▼  (서버) R-9 입금 확인 · R-2 번호 확인
[출고]  S-10 오늘 보낼 목록 → S-11 포장 목록(어머니) → 발송 완료
[부가]  S-14 답장 도우미(AI) · S-16 배송 사고 · S-09 재고(아버지)
```

**설계 원칙**

1. **규칙은 전부 서버(NestJS)에서 강제**한다. 화면의 막기·경고는 편의일 뿐, API를 직접 불러도 같은 결과가 나와야 한다.
2. **AI는 초안만 만든다.** 저장·재고·발송일·고객 묶기·취소는 AI가 결정하지 않는다(6장).
3. **자동 취소는 어디에도 없다.** 중복·미입금·기한 초과는 모두 "표시"만 하고 사람이 처리한다.
4. 고객이 "기준 없음"이라 한 값(3일, 70%, 2일 등)은 `settings` 테이블에 두고 바꿀 수 있게 한다.
5. 시간 기준은 **한국 시간(Asia/Seoul)**. DB는 `timestamptz`로 저장하고 날짜 계산은 KST로 한다. (Render 서버는 UTC이므로 서버 시계에 기대지 않고 KST로 변환해 계산)
6. 배포: **프론트 Vercel / 백엔드·DB Render** (10장).

## 2. 데이터 설계

### 2.1 관계도

```
users ─┐(작성자/확인자 기록)
       │
customers 1 ──── N orders 1 ──── N shipments 1 ──── N shipment_items N ──── 1 products N ──── 1 varieties
                     │                 ▲   │                                         
                     │                 │   └─ 1 ──── N incidents 1 ──── N incident_photos
                     │                 │                   │        └─ 1 ── N incident_logs
                     │                 └── reship ─────────┘ (incidents.reship_shipment_id)
                     └── duplicate_of (orders → orders, 중복 의심 상대)

knowledge_docs 1 ──── N knowledge_chunks         qa_logs (질문·답·근거)        settings (기준값)
```

- **주문 1 : 배송지 N : 품목 N** = `orders` 1 : N `shipments` 1 : N `shipment_items` (FR-1.8)
- **결제는 주문 단위 1건** = 결제 컬럼은 `orders`에만 둔다 (FR-1.9)
- **재발송은 새 배송 건** = 원래 주문 아래 `shipments.is_reship = true`인 행을 새로 만들고, 사고와 연결 (FR-6.3)

| R-14 | **다시 넣기**: 지난 주문의 배송지·품목을 복사해 초안을 만들되 **현재 가격**, **배송지마다 `address_confirmed` 체크 필수**, 판매 전 품종이면 `예약` 안내, 수량 부족이면 경고 + 저장 거부(R-6). **다른 상품으로 자동 대체 안 함** | `OrdersService.create`에서 `source='reorder'`면 모든 배송지 `address_confirmed=true` 검사 | 주소 확인 체크박스, 경고 | 미체크 → 400 | FR-2.2~2.4 |
| R-15 | **고객 주문서**: 로그인 없는 공개 API라 ① **IP당 1분 10회** 요청 제한 ② 전화번호 필수(R-1 형식) ③ 경로 `kakao` · 입력 방식 `customer` · 상태 **`확인필요` 고정** · 결제 `입금대기` — 요청 값으로 바꿀 수 없음 ④ 재고 검사(R-6)·예약(R-7)·발송일(R-8)·중복 의심(R-3)은 다른 주문과 같은 함수 ⑤ 한도 초과 시 고객에게 **남은 수량 숫자를 알려 주지 않고** "수량을 줄여 주세요"만 안내 ⑥ 받는 곳 최대 10곳 | `PublicController` (`@Public()`) → `OrdersService.create` | 상품 상태(주문 가능/얼마 안 남음/품절/예약) | 429 / 400 / 409 | FR-1.2, 1.4, 3.4 |
| R-16 | **전화 주문 저장 상태는 서버가 역할로 결정**: 포장(어머니) → `확인필요`, 관리자(정우 씨) → `접수`. 요청에 넣은 상태 값은 무시 | `OrdersController.createPhone` | 저장 후 안내 문구 | — | FR-1.3 |

**주문 상태 흐름**

```
(어머니 전화 입력 / AI 정리 미확정)          (정우 씨 입력·엑셀)
        needs_check ──── 정우 씨 확정 ────▶ confirmed ──▶ (배송 건) pending → packed → shipped
             └───────────── 취소 ──────────▶ cancelled ◀── 취소(재고 자동 복구: 사용량 합에서 빠짐)
```

- 엑셀(스마트스토어) 주문: `confirmed` + `prepaid/paid`로 저장
- 정우 씨 수기 입력: `confirmed`, 현금이면 `pending`
- 어머니 전화 입력: **서버가 무조건 `needs_check`로 저장** (요청 값 무시)

## 4. 권한

### 4.1 방식
- 로그인 → JWT(역할 포함) 발급. 모든 API에 `JwtAuthGuard` + `@Roles()` + `RolesGuard`.
- **권한은 서버에서 막는다.** 화면에서 메뉴를 숨기는 것은 보조이며, 다른 역할의 API를 직접 부르면 **403**.

## 6. AI가 맡을 일

### 6.0 원칙 (AI가 하지 않는 일)

| AI가 하는 일 | AI가 **하지 않는** 일 (서버 규칙이 함) |
|---|---|
| 카톡 문장 → 주문 **초안** | 저장, 고객 묶기(R-1), 재고 판단(R-6), 발송일(R-8), 중복 판단(R-3), 취소 |
| 근거 조각으로 답변 **문장 작성** | 근거 고르기 순서(쪽지 우선), "자료에 없음" 판정의 1차 판단 |
| 안내 문자 **초안** | 대상자 선정, 실제 발송 |

- 모델: OpenAI GPT API. 키와 모델명은 **`backend/.env`의 `OPENAI_API_KEY`, `OPENAI_MODEL`**에만 둔다. 프론트는 AI를 직접 부르지 않는다.
- 모든 AI 응답은 **JSON 형식(response_format: json_object)** 으로 받고 서버에서 검증한다. 검증 실패·API 오류 시 **AI 없이도 일이 되게** 대체 동작을 둔다.

### 6.1 AI-1 카톡 주문 정리 (FR-1.2 확장, 기획 6장 제안, **P1**)

| 항목 | 내용 |
|---|---|
| 화면 | S-05 "AI로 정리" 버튼 |
| 입력 | 카톡 원문 + 현재 판매 상품 목록(id, 품종, 등급, kg) |
| 출력(JSON) | `orderer_name`, `orderer_phone`(없으면 null), `same_as_last_time`(bool, "작년이랑 같은 걸로"), `shipments[]: {recipient_name, recipient_phone, address, items[]: {product_id 또는 null, raw_text, qty_boxes}}`, `uncertain[]`(확인할 점: "보자기 여부 불명" 등) |
| 지시 핵심 | 원문에 없는 번호·주소·수량을 **지어내지 말 것**(없으면 null). 상품은 목록의 id 중에서만 고를 것. "다섯 군데" 같은 다주소는 배송지별로 나눌 것 |
| 서버 검증 | product_id가 실제 판매 상품인지, 수량이 양의 정수인지, 번호는 R-1 정규화. 틀린 값은 null로 바꾸고 `uncertain`에 추가 |
| 이후 흐름 | 초안이 폼에 채워짐 → **사람이 확인·수정 후 저장** (저장은 일반 `POST /orders`, 모든 규칙 적용). 원문은 `raw_text`로 보관. 번호 null이면 `번호 확인 필요`로 저장 가능. `same_as_last_time=true` + 번호 있음 → 고객의 지난 주문 "다시 넣기"(R-14) 버튼 표시 |
| 실패 시 | "AI 정리 실패 — 직접 입력해 주세요" + 원문은 그대로 두고 빈 폼 |

### 6.2 AI-2 보관·손질 답장 도우미 (FR-5.1~5.5, **P0**)

| 단계 | 처리 | 담당 |
|---|---|---|
| ① 자료 준비 | 농원 쪽지 6장(품종별) → 쪽지 1장 = 문서 1개, 문단 단위 조각. 센터 자료 발췌본 → **쪽 번호를 살려** 쪽 단위 조각. 조각마다 임베딩 저장 | 시드 스크립트 (서버) |
| ② 쪽지 먼저 검색 | 질문 임베딩 ↔ `farm_note` 조각 코사인 유사도(+ 낱말 겹침 보정) 상위 5개, 기준값(0.20, `QA_MIN_SCORE`로 조정) 이상. 후보는 넓게 잡고 근거 여부는 ⑤⑥에서 판정 | 서버 |
| ③ 없으면 센터 자료 | ②에서 검증된 근거가 나오지 않을 때만 `center` 조각 상위 4개(기준 0.25) | 서버 |
| ④ 둘 다 없음 | **GPT를 부르지 않고** `"자료에 없음 — 확인 필요"` 반환 (지어낼 기회 자체를 없앰) | 서버 |
| ⑤ 답변 작성 | 찾은 조각만 넘겨 GPT 호출. 지시: "주어진 자료 내용만 쓸 것, 상식으로 보충 금지". 출력 `{found, answer, reply_draft, evidence:[{id, quote}]}` — **quote는 자료 원문을 글자 그대로 복사** | GPT |
| ⑥ 검증 | **인용문(quote)이 실제로 그 조각 원문에 들어 있는지 서버가 문자열로 확인**(공백·문장부호 무시). 확인된 인용문이 하나도 없으면 근거 없음 → 다음 자료(센터) 또는 "자료에 없음 — 확인 필요". 통과하면 근거 카드에 **자료 종류·문서명·품종·쪽 번호·인용문** 표시 | 서버 |
| ⑦ 기록 | `qa_logs` 저장 | 서버 |

- **쪽지와 센터 자료가 다를 때**: ②에서 쪽지 근거가 있으면 센터 자료는 아예 넘기지 않으므로 쪽지 내용으로 답한다 (I17). 시드에 서로 다른 항목 1개를 넣어 시연·테스트한다(예: 부사 냉장 보관 기간).
- 답장 초안(FR-5.5, P2): 카톡에 붙여넣을 존댓말 2~4문장. 복사 버튼.
- 실패 시: 검색된 근거 조각만 보여 주고 "답변 생성 실패 — 근거를 직접 확인해 주세요".

### 6.3 AI-3 수확·지연 안내 문자 초안 (기획 6장 제안, **P2**)

| 항목 | 내용 |
|---|---|

## 9. 정해 둔 가정 (시연 때 고객 확인)

| 가정 | 이유 |
|---|---|
| 실제 수확량을 입력하면 판매 한도 = 실제 수확량 (안전 비율 적용 안 함) | 안전 비율은 "따 봐야 안다"는 불확실성 때문(FR-3.2). 실제로 땄으면 불확실성이 없음. 필요하면 비율 적용으로 바꿀 수 있게 `ProductsService` 한 곳에서 계산 |
| `확인필요`(어머니 입력) 주문도 재고에서 바로 차감 | 확인 전에 다른 주문이 그 수량을 가져가 초과 판매되는 것을 막기 위해. 취소하면 바로 돌아옴 |
| 중복 의심 주문은 발송을 막지 않고 강조만 | "바로 취소 안 함, 확인 후 처리"(I3)와 자동 취소 금지 원칙. 막으면 정상 재주문까지 늦어짐 |
| 입금·번호 확인이 늦으면 발송 예정일을 확인 시각 기준으로 다시 계산 | 3시 이후 입금 확인된 주문이 그날 목록에 끼어드는 것 방지(3시 마감 규칙과 일관) |
| 공휴일(추석 당일 등)은 오늘 범위에서 제외 | 고객이 말하지 않았고 택배사 일정에 따라 다름. 다음 단계로 `settings`에 휴무일 추가 |

## 10. 배포 구성

```
[브라우저] ──▶ Vercel (Next.js, frontend/) ──HTTPS──▶ Render Web Service (NestJS, backend/) ──내부 주소──▶ Render PostgreSQL
                                                                     └──▶ OpenAI API
```

| 구성 | 위치 | 설정 |
|---|---|---|
| 프론트엔드 | **Vercel** | Root Directory `frontend`. 환경 변수 `NEXT_PUBLIC_API_URL` = Render 백엔드 주소 |
| 백엔드 | **Render Web Service** | Root Directory `backend`, Build `npm ci && npm run build`, Start `npm run start:prod`. 헬스 체크 `GET /health` |
| DB | **Render PostgreSQL** | 백엔드와 **같은 리전**에 만들고 백엔드는 Internal Database URL 사용. 로컬에서 시드 넣을 때만 External URL(SSL 필요) |

**백엔드 환경 변수** (Render 대시보드에만 입력, GitHub에는 `backend/.env.example`에 이름만)

| 이름 | 내용 |
|---|---|
| `DATABASE_URL` | Render PostgreSQL 주소 |
| `JWT_SECRET` | 로그인 토큰 서명용 임의 문자열 |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | GPT API 키·모델명 |
| `CORS_ORIGIN` | Vercel 프론트 주소 (이 주소에서 온 요청만 허용) |
| `TZ` | `Asia/Seoul` (날짜 계산은 코드에서도 KST로 명시) |

**주의**
- 무료 웹 서비스는 15분쯤 쓰지 않으면 잠들어 첫 요청이 30~50초 걸린다 → **발표 직전 한 번 접속해 깨워 둔다.**
- DB 테이블 생성·시드는 백엔드 시드 스크립트(`npm run seed`)로 한다. 배포 후 한 번 실행.
- DB 주소·API 키·시드 계정 비밀번호는 GitHub·발표 자료에 넣지 않는다.
